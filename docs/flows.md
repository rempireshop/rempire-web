# Кабинет покупателя и письма, которые магазин шлёт сам

Что здесь описано: вход в личный кабинет без пароля и три письма, которые
уходят покупателю **без вашего участия** — «брошенная корзина», «товар снова в
наличии» и поздравление ко дню рождения. Три переключателя в админке
(«Письма») раньше ничего не включали; теперь включают.

---

## Коротко для Рената

**Кабинет.** Покупатель вводит почту → на неё приходит письмо с шестизначным
кодом → он вводит код и попадает в кабинет. Пароля нет и заводить его не надо.
В кабинете он видит свои заказы (номер, дату, сумму, статус, трек-номер),
может вписать имя, телефон и день рождения и поставить галочку «хочу
получать новости и скидки». Купить по-прежнему можно и без кабинета — ничего
не изменилось.

**Три письма.** В админке → «Письма» три переключателя. По умолчанию все
**выключены**. Под каждым теперь написано, сколько человек стоит в очереди на
это письмо.

| Переключатель | Что делает | Когда уходит |
|---|---|---|
| **Брошенная корзина** | напоминание с кнопкой «вернуться к корзине» | через 3 часа после того, как человек собрал корзину и не оформил заказ. Одно письмо на корзину, и только если заказа так и не было |
| **Товар снова в наличии** | письмо всем, кто оставил почту на странице закончившегося товара | как только вы ставите этому товару «в наличии» в админке. Каждому — один раз |
| **Скидка ко дню рождения** | личный промокод на 10 %, действует 14 дней | утром в день рождения, только тем, кто сам поставил галочку про новости и скидки |

**Важно про день рождения.** Письмо уйдёт, только если магазину есть что в него
положить: либо работает раздел «Промокоды» (тогда код выписывается сам, личный
и одноразовый), либо в настройках задан фиксированный код. Если ни того ни
другого нет — письмо не уходит вовсе. Поздравление с нерабочим кодом хуже, чем
молчание.

**Кто может это включить.** Вы, кнопками в админке. Ничего программировать не
надо. Диму нужно один раз прописать на сервере `CRON_SECRET` — см. ниже.

## Как это устроено

### Вход без пароля

| Шаг | Что происходит |
|---|---|
| `POST /api/account/code` | `{email, lang}`. Генерирует шесть цифр, кладёт в `login_codes` **хэш** кода (не сам код), шлёт письмо `login-code`. Ответ всегда `{ok:true}` для валидного адреса — по ответу нельзя узнать, есть ли у адреса аккаунт. Лимит: 3 запроса за 15 минут на адрес **и** 3 на IP |
| `POST /api/account/login` | `{email, code, lang}`. Код живёт 15 минут и умирает после пяти неверных попыток. Успех → cookie `rmp_cust` на 90 дней + профиль и заказы в ответе |
| `GET /api/account/me` | Профиль и последние 20 заказов по этому адресу. Адрес берётся **из cookie**, не из запроса |
| `PATCH /api/account/me` | `{name, phone, birthday, marketing, lang}` — только те ключи, что прислали |
| `POST /api/account/logout` | Стирает cookie. Проверок не требует: «забудь меня» должно работать всегда |

Cookie `rmp_cust` = `v1.<срок>.<адрес>.<подпись>`, подпись HMAC-SHA256 на
`SESSION_SECRET` — та же схема, что у админской `rmp_admin`, но со своим
префиксом, поэтому одну нельзя подставить вместо другой. `httpOnly`,
`SameSite=Lax`, `Secure` везде кроме `http://localhost`.

Заказы ищутся **по адресу почты**, а не по id покупателя: заказ, оформленный
гостем до появления кабинета, всё равно принадлежит хозяину этого ящика.

### Брошенная корзина

1. Как только в оформлении заказа поле e-mail становится похожим на адрес,
   браузер шлёт `POST /api/carts` — id товаров, размеры и количества.
   То же самое происходит при добавлении товара в корзину, если человек уже
   вошёл в кабинет.
2. **Цены в запрос не входят.** Сервер собирает снимок корзины сам, из
   каталога и ваших наценок — ровно как при оформлении заказа.
3. `POST /api/orders` помечает корзину «выкуплена» (`recovered_at`), и
   напоминание уже не уйдёт.
4. Через 3 часа тишины (и если заказа с этого адреса так и не было)
   планировщик шлёт одно письмо. `reminded_at` ставится **до** отправки:
   потерять одно письмо лучше, чем прислать человеку четыре.
5. В письме — ссылка `/shop2/checkout/?resume=<токен>`. Токен подписан и
   содержит только товары и количества — **никакой почты в адресной строке**.
   Магазин, открыв такую ссылку, восстанавливает строки корзины, берёт только
   существующие товары и не больше 9 штук каждого.

### Снова в наличии

Кнопка «Сообщить о наличии» на странице закончившегося товара открывает поле
для почты → `POST /api/stock-alerts`. Повторная подписка на тот же товар — это
одна подписка, а не два письма.

Письмо уходит из `upsertOverride` (`src/lib/orders.ts`), когда владелец
ставит товару «в наличии». Ожидающие подписки существуют только у товара,
который кто-то застал закончившимся, поэтому «есть кого оповестить» и есть
переход «нет → есть» — это одно и то же событие. Планировщик дополнительно
подметает: если товар вернулся в наличии как-то иначе, письмо уйдёт в
ближайший запуск.

### День рождения

Раз в сутки выбираются покупатели, у кого сегодня день рождения, стоит
согласие на рассылку и в этом году письмо ещё не уходило
(`customers.birthday_sent_year` — защита от повторов, сколько бы раз ни
запускался планировщик).

Промокод: если есть `src/lib/promos.ts` — код выписывается там
(`percent`, 10 %, 14 дней, одно применение, код вида `REM-BD-7QK4X9`).
Если модуля нет — берётся `settings.flows.birthdayCode`. Если нет ни того ни
другого, письмо не уходит и строка не помечается: письмо «зависает» и уйдёт,
как только код появится.

### Планировщик

```
GET /api/cron/flows
authorization: Bearer <CRON_SECRET>
```

Идемпотентен и дёшев: каждая отправка помечает свою строку до того, как письмо
уходит, поэтому его можно звать хоть каждый час, хоть дважды подряд. Без
`CRON_SECRET` маршрут отвечает 503 всем — открытая ручка, которая шлёт письма
покупателям, не должна существовать. Отвечает
`{ok, abandoned:{sent,skipped}, backstock:{…}, birthday:{…},
invoices:{reminded,cancelled,skipped}, ms}`.

Четвёртый шаг, `invoices`, — это не письмо из «Писем», а «Счета для компаний»:
напоминание перед сроком оплаты и автоотмена после него
(`src/lib/invoice-dunning.ts`, docs/payments.md § 10). Он живёт в своём файле,
а в `runFlows()` это один вызов; интервалы задаются в «Настройки → О компании →
Счета для компаний», а не переменными окружения, и `0` в любом из них
выключает свой шаг.

**Vercel.** `vercel.json` → `crons: [{ "path": "/api/cron/flows/", "schedule": "0 7 * * *" }]`.
На тарифе **Hobby крон разрешён не чаще одного раза в сутки** — выражение вроде
`0 * * * *` (ежечасно) не даст задеплоиться вовсе, а время срабатывания
плавает в пределах часа (7:00–7:59 UTC, то есть около 10 утра по Таллинну
летом). Это самое частое, что разрешено на Hobby; на Pro можно ставить
`0 * * * *` и менять больше ничего не надо. Vercel сам подставляет заголовок
`authorization: Bearer $CRON_SECRET`, как только переменная задана в проекте.

Раз в сутки достаточно для дня рождения и для «снова в наличии» (там письмо
уходит сразу из админки, планировщик только подметает), но напоминание о
корзине при этом приходит не через 3 часа, а в ближайший запуск. Хотите
честные 3 часа — либо Pro, либо запускать эту же ручку снаружи.

**Railway (продакшен).** У Railway есть свой планировщик: в проекте
**New → Cron Job** (или у сервиса *Settings → Cron Schedule*), выражение
`0 * * * *` и команда

```bash
curl -fsS -H "authorization: Bearer $CRON_SECRET" https://rempireshop.com/api/cron/flows/
```

`CRON_SECRET` берётся из переменных того же проекта. Любой внешний планировщик
(cron-job.org, GitHub Actions, systemd timer) годится точно так же — это
обычный HTTP-запрос с заголовком.

## Переменные окружения

Значения не коммитить. Локально — в `.env.local`, на хостинге — в настройках
проекта.

| Имя | Зачем | Заметки |
|---|---|---|
| `CRON_SECRET` | защита `/api/cron/flows` | **Новая.** Случайная строка. Без неё планировщик отвечает 503 и письма не уходят вовсе. `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`. Vercel сам подставляет её в заголовок крона |
| `SESSION_SECRET` | cookie кабинета, хэш кода входа, подпись ссылки восстановления | Уже есть (docs/backend.md). Смена — выход всех покупателей и админа |
| `RESEND_API_KEY`, `RESEND_FROM`, `MAIL_REPLY_TO`, `PUBLIC_BASE_URL` | сами письма | Уже есть (docs/mail.md). Без ключа отправка «пропускается» и пишется в лог, ничего не падает |
| `DATABASE_URL` | таблицы ниже | Уже есть |

## Настройки (`settings.flows`)

Пишутся админкой через `PUT /api/admin/settings`, читаются `getFlows()` в
`src/lib/flows.ts`. Нет строки — всё выключено; это безопасное направление.

```json
{
  "abandoned": false,
  "backstock": false,
  "birthday": false,
  "pending": false,
  "birthdayCode": "",
  "birthdayPercent": 10
}
```

`pending` — то самое письмо «заказ принят, ждём оплату» из docs/mail.md.
Раньше оно не могло уйти никогда: `orders.ts` звал хук с одним аргументом, и
`sendPending` не передавался (аудит, пункт 3). Теперь переключатель работает;
если строки нет — решает `MAIL_PENDING_PAYMENT`, как и было написано.

## Таблицы (`db/migrations/050_customers.sql`)

- **`customers`** — `email` (в нижнем регистре, уникальный), `name`, `phone`,
  `lang`, `birthday`, `marketing`, `last_login_at`, `birthday_sent_year`.
- **`login_codes`** — одна строка на адрес: хэш кода, срок, счётчик попыток.
- **`carts`** — одна строка на адрес: снимок корзины, `updated_at`,
  `recovered_at`, `reminded_at`.
- **`stock_alerts`** — подписки на «снова в наличии», уникальные по паре
  (адрес, товар), `sent_at`.

## Что проверить руками перед запуском

```bash
npm run migrate                 # применить 050_customers.sql
npm test                        # vitest на PGlite
curl -i https://<host>/api/cron/flows/            # → 401 без заголовка
curl -i -H "authorization: Bearer $CRON_SECRET" https://<host>/api/cron/flows/   # → 200
```

И один живой проход: почта → код в ящике → вход → заказ виден в кабинете.
Письмо с кодом сначала стоит посмотреть в админке («Письма» → «Код для входа»)
на всех трёх языках.

## Чего здесь нет

- Отписки одним кликом. В маркетинговых письмах ссылка «Отписаться» ведёт в
  кабинет, где стоит галочка про новости — отдельной ручки `unsubscribe` пока
  нет. Для трёх-пяти заказов в месяц это терпимо, но до серьёзной рассылки
  сделать надо.
- Удаления аккаунта покупателем (GDPR). Сейчас — руками в базе.
- Второго напоминания о корзине. Одно письмо на корзину, сознательно.
