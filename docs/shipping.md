# Доставка — тарифы, перевозчики, пакоматы

Три вещи, которые здесь описаны: **сколько стоит доставка** (правила в базе,
`src/lib/shipping.ts`), **откуда берётся список пакоматов**
(`src/lib/parcel-points.ts`, `tools/fetch-parcel-points.mjs`) и **как из админки
оформляется отправление и печатается этикетка** (Montonio Shipping,
`src/lib/shipping/montonio.ts`, раздел 3).

---

## 1. Тарифы: `settings.shipping_rules`

Цены живут в базе, в таблице `settings` под ключом `shipping_rules`, — чтобы
менять их из админки без выкладки. Строку создаёт миграция
`db/migrations/030_shipping_rules.sql`; если строки (или всей базы) нет, код
берёт те же значения из себя и заказ всё равно считается.

```json
{
  "freeFrom": 59,
  "freeFromByCountry": { "FI": 99, "LV": null },
  "methods": {
    "parcel":  { "default": 4.99, "EE": 3.49, "LV": 4.99, "LT": 4.99 },
    "courier": { "default": 9.90, "EE": 5.99 },
    "pickup":  { "default": 0 }
  },
  "carriers": {
    "omniva": { "EE": 3.29 },
    "dpd":    { "default": 6.50 }
  }
}
```

| Ключ | Что делает |
| --- | --- |
| `freeFrom` | Сумма корзины (€, **до скидки**), с которой доставка бесплатна. `null` — бесплатной доставки нет вообще. |
| `freeFromByCountry` | Переопределение порога по стране. `null` для страны — там никогда не бесплатно. |
| `methods` | Цена по способу и стране. `default` — для всех стран, что не названы. |
| `carriers` | Необязательное переопределение цены по перевозчику; сильнее `methods`. |

Правила разбираются по одному ключу: кривое или недописанное значение
откатывается к значению по умолчанию, а не роняет оформление заказа. Порог
считается **до** промокода — так принято, и корзина не теряет уже заработанную
бесплатную доставку из-за скидки.

Три способа доставки: `parcel` (пакомат), `courier` (курьер до двери),
`pickup` (самовывоз на Mardi 1; всегда бесплатно и только по Эстонии). Витрина
шлёт свои названия на трёх языках («Пакомат Omniva», «DPD kuller») — их
приводит к трём значениям `normalizeMethod()`.

### Цены по умолчанию и цены перевозчиков — это разные числа

В коде и в миграции лежат числа из брифа: пакомат EE 3.49, LV/LT 4.99, курьер
EE 5.99, остальное 9.90, бесплатно от 59 €.

**Это не прайс перевозчиков.** Реальные тарифы 2025–2026 (они в
`public/shop/shipping-data.js` и в демо-таблице `SHIP` в `app.js`) выше:
Omniva EE ≈ 5.50, DPD курьер EE ≈ 9.00, Латвия и Литва 10–15 €, Финляндия до
26 €. То есть за пределами Эстонии значения по умолчанию — ниже себестоимости.

**Это осознанное расхождение, и закрыть его — решение Рената, не разработчика.**
Бриф задал числа для запуска; окончательные тарифы (и то, продолжает ли магазин
доплачивать за доставку в Латвию, Литву и Финляндию ради конверсии) выбирает
владелец. Пока цифры не пересмотрены, каждый балтийский заказ приносит убыток
на доставке: LV/LT пакомат 4,99 € против прайса 10,60–11,80 €.

Менять их нужно в `settings.shipping_rules` — из админки, а не в коде.

### Редактор тарифов в админке

**«Настройки → Доставка»** — таблица, а не справка. Строки: EE, LV, LT, FI,
«Другие страны Европы» и «Остальные страны» (это ключ `default`); колонки:
пакомат, курьер, самовывоз и «Бесплатно от». Ниже — сворачивающийся блок «Цены
по перевозчикам» (Omniva, SmartPosti, DPD, Venipak по странам, где они вообще
предлагаются): заполненная клетка сильнее таблицы выше.

- Пустая клетка — «нет своей цены», берётся строка «Остальные страны»
  (`default`).
- Слово **«нет»** в колонке «Бесплатно от» — в эту страну доставка не бывает
  бесплатной ни при какой сумме (`freeFromByCountry: {"LV": null}`).
- Цены принимаются от 0 до 99 €, с запятой или точкой, до двух знаков.
  Всё остальное просто не записывается в черновик.
- **«Сохранить тарифы»** пишет весь набор целиком через
  `PUT /api/admin/settings {shipping_rules}`, попадает в «Журнал изменений» и
  отменяется оттуда же. **«Вернуть значения по умолчанию»** возвращает числа из
  `DEFAULT_SHIPPING_RULES`.
- Помощник умеет то же самое одной фразой — «сделай доставку в Латвию 6,90»
  (действие `set_shipping_rules`, частичное: меняется только названная клетка).

До этого редактора панель печатала прайс-лист перевозчиков (`SHIP.EE` в
`app.js`), а касса считала по `SHIP_RULES`: владелец читал одно число, магазин
брал другое. Теперь и то и другое — одна строка в базе.

Через SQL, если нужно:

```sql
update settings set value = '{ … }'::jsonb, updated_at = now()
where key = 'shipping_rules';
```

Витрина берёт те же правила через `GET /api/overrides` (`settings.shipping_rules`)
— при загрузке страницы, а не только при оформлении, — так что обещание
«бесплатно от 59 €» в шапке, в подвале и на карточке товара всегда равно тому,
что посчитает сервер. Если API недоступен (прототип лежит статикой), она
работает на встроенных значениях по умолчанию.

`src/lib/shipping.ts` держит строку в памяти инстанса минуту; сохранение из
админки сбрасывает этот кэш (`resetShippingRulesCache()` в
`PUT /api/admin/settings`), поэтому новая цена действует со следующего заказа,
а не через минуту.

## 2. Пакоматы: `GET /api/shipping/points/`

```
GET /api/shipping/points/?country=EE&carrier=omniva|dpd|smartpost|venipak|all
→ { ok, country, carrier, source, count, points: [
      { id, carrier, name, address, city, zip, lat, lng, type } ] }
```

`type` — `parcel_machine`, `pickup_point` (пункт выдачи в магазине) или
`post_office`.

`source` говорит, откуда ответ:

| Значение | Что это |
| --- | --- |
| `montonio` | Montonio Shipping — все перевозчики по одной паре ключей (раздел 3) |
| `live` | публичный фид перевозчика |
| `cache` | тот же фид, в памяти инстанса 6 часов |
| `seed` | запасной файл в репозитории |
| `montonio+seed` | часть перевозчиков от Montonio, остальные из запасного файла |

Ответ кэшируется на CDN на час (`s-maxage=3600`), ответы Montonio — ещё и на
6 часов в памяти инстанса.

Неизвестный перевозчик — **не ошибка**: маршрут отвечает `{ ok: true, points: [] }`,
и витрина просто убирает эту кнопку. Ошибка 400 оставила бы в оформлении заказа
перевозчика, из списка которого нечего выбрать.

### Кнопки перевозчиков в оформлении

`CARRIERS_BY_COUNTRY` в `public/shop2/app.js` перечисляет, о ком **вообще стоит
спросить**, а не кто точно есть: EE — Omniva, SmartPosti, DPD, Venipak; LV и
LT — Omniva, DPD, Venipak; FI — SmartPosti, DPD. При открытии шага доставки
витрина спрашивает списки сразу по всем перевозчикам страны, и тот, у кого
список пуст, исчезает до того, как на него нажмут. Поэтому DPD и Venipak
появляются ровно там, где Montonio их отдал, а Финляндия получает пакомат в тот
день, когда Montonio вернёт финские точки, — без ещё одной выкладки.

### Что реально есть у каждого перевозчика

Проверено 03.09.2026.

| Перевозчик | Публичный фид | Как получаем |
| --- | --- | --- |
| **Omniva** | Есть: <https://www.omniva.ee/locations.json> — один файл на EE, LV и LT, без ключа, CORS открыт | Живой запрос + кэш 6 ч, или Montonio |
| **SmartPosti** (Itella/Posti) | Нет массовой выдачи: сайт отдаёт список слагов, а детали — по одному запросу (~60 КБ) на точку | Seed-файл, или Montonio |
| **DPD** | Нет вообще. Публичные адреса (`api.dpd.lt`, `parcelshop-finder.dpd.com`) больше не существуют | **Только Montonio** (или договор DPD, см. ниже) |
| **Venipak** | Нет | Только Montonio |

Две ловушки Omniva, из-за которых нельзя просто скопировать поля:

- `X_COORDINATE` — это **долгота**, `Y_COORDINATE` — **широта**. Названия
  читаются наоборот.
- `ZIP` у пакомата — **не почтовый индекс**, а внутренний код терминала
  (он уникален для всех 1442 строк). Мы используем его как `id` и никогда как
  индекс на посылке. Настоящий индекс есть только у 32 почтовых отделений
  (`TYPE=1`).

**DPD.** Свой адрес у DPD есть — `https://integration.dpd.ee/ws-mapper-rest/parcelShopSearch_`
(и `.lv`, плюс `integracijos.dpd.lt`), но он требует логин и пароль от договора
DPD Baltics. Если они появятся — положить их в `DPD_API_USER` и `DPD_API_PASS`,
и точки начнут приходить и в API, и в seed без единой правки кода. **Проще
другое: те же точки DPD отдаёт Montonio** — по ключам, которые уже есть для
оплаты (раздел 3). Пока нет ни того, ни другого, DPD предлагается только как
курьер, а кнопка «DPD» в выборе пакомата пропадает сама.

**Финляндия.** Omniva там не работает. У SmartPosti финских точек 3333, но
детальные страницы для них на эстонском домене не существуют: все 3333 адреса
отдают 404 (проверено — скрипт скачал список и не смог получить ни одной
карточки). Официальный путь мимо Montonio — Posti Pickup Point API
`https://gateway.posti.fi/2025-04/pickuppoints/FI`, ему нужен Bearer-токен
(старый Location Service отключён 31.03.2026). **С Montonio финские пакоматы
появятся сами**, как только Ренат подключит там перевозчика с точками в
Финляндии: витрина спрашивает про FI на каждом оформлении и показывает пакомат,
если в ответе есть хоть одна точка. Без Montonio и без токена Posti в Финляндию
по-прежнему предлагается только курьер.

## 3. Montonio Shipping — все перевозчики по одной паре ключей

Файл `src/lib/shipping/montonio.ts`, документация Montonio —
<https://docs.montonio.com/api/shipping-v2/reference> (сверено 03.09.2026).

**Зачем.** Публичные фиды закрывают только Omniva. Montonio перепродаёт Omniva,
DPD, Itella SmartPosti и Venipak по **тем же ключам, что уже стоят для оплаты**
(`MONTONIO_ACCESS_KEY`, `MONTONIO_SECRET_KEY`, `MONTONIO_ENV`) — отдельного
договора и отдельного ключа не нужно. И он же оформляет отправление и печатает
этикетку, так что Ренат не переписывает адреса в личные кабинеты перевозчиков.

### Что делает Ренат

1. В партнёрской системе Montonio (<https://partner.montonio.com>, для тестов
   <https://sandbox-partner.montonio.com>) — раздел **Shipping** → включить
   перевозчиков, которых хочет предлагать. Договор можно взять у самого
   Montonio (`hasMontonioContract`) или подключить свой.
2. Указать там же адрес отправителя — он подставляется в каждое отправление,
   в коде его нет.
3. Больше ничего. Ключи те же, что для оплаты.

### Что видит Ренат в админке

В карточке заказа появляется блок «Отправление»:

- у оплаченного заказа с пакоматом или курьером — кнопка **«Создать
  отправление»**. Одно нажатие: Montonio регистрирует посылку у перевозчика и
  возвращает трек-номер;
- после этого — трек-номер, ссылка **«Этикетка PDF»** (A6, одна наклейка на
  страницу — как раз под термопринтер) и ссылка «Отследить»;
- статус заказа сам переходит в «Отправлен», а покупателю уходит письмо с
  трек-номером;
- у некоторых перевозчиков приходит **код сдачи посылки** (`dropOffPin`) — с
  ним посылку можно сдать в пакомат вообще без печатной наклейки;
- самовывоз отправления не требует, и кнопки там нет.

Второе нажатие ничего не создаёт: маршрут возвращает уже сохранённое
отправление, чтобы не заказать (и не оплатить) вторую посылку.

### Адреса и авторизация

| | |
| --- | --- |
| Боевой | `https://shipping.montonio.com/api/v2` |
| Песочница | `https://sandbox-shipping.montonio.com/api/v2` |

Авторизация — **JWT в заголовке**, не в теле запроса (этим Shipping API
отличается от Orders API, где подписанный payload лежит в `{ data: … }`):

```
Authorization: Bearer <HS256 { accessKey, exp }>
```

Подписывается тем же `MONTONIO_SECRET_KEY`, алгоритм HS256, срок жизни — час
(рекомендация из документации). Используется тот же `src/lib/payments/jwt.ts`,
новых зависимостей не появилось.

**Про лимиты запросов в документации не сказано ничего** — ни в обзоре, ни в
справочнике. Поэтому списки точек кэшируются на 6 часов, как и фиды.

### Эндпоинты, которые мы используем

| Метод | Путь | Зачем |
| --- | --- | --- |
| `GET` | `/shipping-methods` | какие перевозчики включены в стране |
| `GET` | `/shipping-methods/pickup-points?carrierCode=&countryCode=&type=` | список точек |
| `GET` | `/shipping-methods/courier-services?carrierCode=&countryCode=` | id курьерской услуги |
| `POST` | `/shipments` | создать отправление |
| `GET` | `/shipments/{id}` | перечитать статус и трек-номер |
| `POST` | `/label-files` | создать файл этикеток |
| `GET` | `/label-files/{id}` | ссылка на готовый PDF |

Точка выдачи приходит так (поля скопированы из справочника, а не придуманы):

```json
{ "pickupPoints": [ {
    "id": "98b391d7-5299-447c-9ad7-6b4042ef8b2f",
    "name": "Laagri Coop Maksimarketi pakiautomaat",
    "type": "parcelMachine",
    "streetAddress": "Pärnu mnt 558a",
    "locality": "Laagri alevik",
    "postalCode": "96067",
    "carrierCode": "omniva",
    "additionalServices": [ { "code": "cod" } ] } ],
  "countryCode": "EE" }
```

Две вещи, которые из этого следуют:

- **Координат в ответе Montonio нет вообще.** Ни `latitude`, ни `longitude` —
  проверено по списку полей в справочнике. Поэтому у точек Montonio `lat` и
  `lng` равны `null`, и координаты остаются только у точек из фидов. Карту
  выбора пакомата на них строить нельзя.
- `id` — это UUID Montonio, и **только им** можно адресовать отправление.
  Если покупатель выбрал точку из фида (id вида `omniva-96243`), при создании
  отправления она сопоставляется обратно по названию; если совпадения нет,
  маршрут отвечает `point_unresolved`, а не отправляет посылку не туда.

**Перевозчик в заказе хранится.** Витрина шлёт `shipping.carrier` («omniva»,
«smartpost», «dpd» или «venipak»; для курьера — пустую строку), и
`createOrder()` в `src/lib/orders.ts` кладёт его в `orders.shipping.carrier`:
обрезанным, в нижнем регистре, не длиннее 20 символов и только из этого списка,
всё остальное превращается в `null`. При создании отправления перевозчик
берётся по порядку: что указал админ в теле запроса → `shipping.carrier` из
заказа → для заказов, оформленных до того, как поле стали хранить, — префикс
идентификатора точки из фида (`omniva-96243`) и название перевозчика внутри
старой текстовой подписи способа («Пакомат Omniva»). Для пакомата это почти
всегда неважно: UUID точки Montonio сам задаёт перевозчика, и в ответе на
создание отправления приходит настоящий `carrierCode`. Для курьера витрина
перевозчика не спрашивает, поэтому, если админ его не указал, берётся первый
перевозчик с курьерской услугой в этой стране.

Отправление создаётся синхронно (`synchronous: true`): админ нажал кнопку и
должен увидеть трек-номер на экране, а не через вебхук. Поэтому **вебхуки
Montonio Shipping мы не регистрируем.** Они есть — `shipment.registered`,
`shipment.registrationFailed`, `shipment.labelsCreated`, `shipment.statusUpdated`,
`labelFile.ready`, `labelFile.creationFailed`; на магазин их можно завести до
десяти, тело POST-а — `{ payload: <JWT> }`, подписанный тем же секретом, шлются
с адресов `35.156.245.42` и `35.156.159.169`. Понадобятся, если появится
массовая печать этикеток или живой статус доставки на странице заказа.

### Маршруты магазина

```
POST /api/admin/shipments/           { orderId }  → { ok, shipment }
GET  /api/admin/shipments/<id>/label/             → PDF
```

Оба за `requireAdmin`. `<id>` — uuid заказа или его номер (`R-100042`).
Этикетка **проксируется**, а не отдаётся ссылкой: Montonio выдаёт подписанный
адрес S3, и ссылка на него была бы наклейкой, доступной кому угодно, пока
подпись жива.

Результат кладётся в `orders.shipping.montonio` (слиянием, поля оформления не
затираются):

```json
{ "provider": "montonio", "shipmentId": "…", "status": "registered",
  "carrier": "omniva", "trackingCode": "CC543167770EE",
  "trackingUrl": "https://minu.omniva.ee/track/…", "dropOffPin": "4821",
  "labelUrl": "…", "createdAt": "…" }
```

### Чего в коде нет и почему

- **Веса товаров в каталоге нет**, а Montonio его требует. Считаем оценкой:
  0,4 кг на единицу плюс 0,2 кг на упаковку, от 0,3 до 30 кг. Перевозчик
  взвесит посылку сам; если у договора включена обязательная проверка габаритов
  (`parcelDimensionsRequired: true`), запрос вернётся с 400, и текст ошибки
  Montonio будет виден в ответе админского маршрута.
- **Расчёт стоимости через Montonio** (`POST /shipping-methods/rates`) не
  подключён: цены магазина живут в `settings.shipping_rules` (раздел 1).
- Наложенный платёж (`cod`) и проверка возраста (`ageVerification`) не
  используются.

### Песочница

`MONTONIO_ENV=sandbox` (значение по умолчанию) — запросы уходят на
`sandbox-shipping.montonio.com`. Песочница не звонит перевозчикам: адреса и
телефоны не проверяются, этикетки рисуются заглушками, трек-номера не настоящие.
Перевозчиков в песочнице всё равно надо включить, но реквизиты договора можно
вписать любые. Переключать на `live` — только когда выданы боевые ключи;
песочные ключи на боевом хосте не работают, и наоборот.

## 4. Как обновить seed-файл

`src/data/parcel-points.seed.json` лежит в репозитории намеренно: витрина
должна предлагать пакомат и в день, когда сайт перевозчика лежит.

```bash
node tools/fetch-parcel-points.mjs                        # все перевозчики
node tools/fetch-parcel-points.mjs --carrier omniva       # только один
node tools/fetch-parcel-points.mjs --countries ee,fi      # страны SmartPosti
node tools/fetch-parcel-points.mjs --dry                  # посчитать, не писать
```

Что нужно знать перед запуском:

- Omniva — один запрос, секунда.
- SmartPosti — **один запрос на точку**. EE это 356 запросов (пара минут), FI —
  3333 (десятки минут и ~200 МБ трафика). Скрипт держит 6 параллельных
  соединений; не увеличивайте — это чужой сайт.
- Адрес детальной страницы содержит `buildId` сайта SmartPosti, который меняется
  при каждой их выкладке. Скрипт вычитывает его сам — не прописывайте руками.
- LV и LT у SmartPosti пока не собираются: локализованные адреса страниц
  (`/pakomati`, `/pastomatai`) отдают 404, путь ещё нужно найти.
- DPD добавится сам, если в окружении есть `DPD_API_USER` и `DPD_API_PASS`.

После запуска — посмотреть на счётчики в конце вывода и на размер файла, и
только потом коммитить.

## 5. Переменные окружения

Значения не хранятся в репозитории — только имена.

| Переменная | Зачем |
| --- | --- |
| `MONTONIO_ACCESS_KEY` | Access Key из партнёрской системы. **Тот же, что для оплаты** |
| `MONTONIO_SECRET_KEY` | Secret Key, им подписывается JWT. Тот же, что для оплаты |
| `MONTONIO_ENV` | `sandbox` (по умолчанию) или `live`. Общий с оплатой |
| `DPD_API_USER`, `DPD_API_PASS` | Прямой доступ к точкам DPD (нужен договор DPD Baltics). Не нужны, если работает Montonio |
| `POSTI_API_KEY` | Пока не используется — понадобится для точек SmartPosti в Финляндии мимо Montonio |

Без ключей Montonio всё работает как раньше: Omniva из фида, SmartPosti из
seed-файла, DPD и Venipak не предлагаются, кнопки «Создать отправление» нет
(маршрут отвечает `not_configured`).
