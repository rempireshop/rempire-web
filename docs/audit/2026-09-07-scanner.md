# Rempire — making the scanner read first time

Work pass, 07.09.2026, branch `r2-scan2` (based on `448cbd7`).
Follows on from `docs/audit/2026-09-06-scanner.md`, which fixed the binding
flow, the keyboard, the lens choice and the render carry-across. This pass is
about the one thing Dim put above everything else when he answered the open
questions:

> «We need a good scanner which works from first time.»

and about the six other decisions he made in the same round (pinch-to-zoom,
the whole «Склад» list, a progress counter, the «мало» threshold, the
«запасной декодер» hint, one name for the scanner).

The camera half of last night's work was tuned by reasoning about a phone
nobody here has. This time it was measured.

---

## 1. The measuring instrument

`tools/scan-bench.mjs` — a new tool, not a test, and CI does not run it.

It launches headless Chromium, paints **real EAN-13 barcodes** (encoded from
the specification: 95 modules, L/G/R parity by first digit, check digit
computed) into a 1920×1080 frame that stands in for a camera picture, and runs
the **actual vendored decoder** — `public/vendor/zxing/zxing-browser.min.js`,
the one Samsung Internet always uses and the one Chrome hands over to when
Play Services' barcode module is missing — over each candidate framing.

Five axes, each one thing the owner does with his hands:

| axis | what it is | swept |
|---|---|---|
| `mpx` | pixels per barcode module — the only distance-independent way to say "how far away". A 13-digit EAN is 95 modules, so mpx 2 puts the code ~190 px wide in the frame (arm's length, 100 ml bottle); mpx 4.5 is the code filling the middle third. | 1.2 – 4.5 |
| `deg` | how far off horizontal the bottle is held | 0 – 25° |
| `blur` | focus and motion, in pixels of gaussian | 0 – 2.2 px |
| `dark` | a dark stockroom **as a camera sees one**: dimmer, noisier (sensor gain) and softer (longer exposure) | 0, 0.55 |
| `glare` | the specular stripe a bottle puts across its own label | on/off |
| `off` | the label not centred, as a fraction of the short side | 0, 0.14 |

Two decoder settings (zxing's `TRY_HARDER` on and off) × nine framings ×
768 painted frames = **13 824 decodes** in the main run.

```
node tools/scan-bench.mjs                 # the full sweep, ~11 min
node tools/scan-bench.mjs --quick         # a third of the images
node tools/scan-bench.mjs --focus         # the noise/rotation questions only
node tools/scan-bench.mjs --json out.json # every cell, for a second opinion
```

**The first thing it caught was a mistake in itself.** The first run modelled
a dark stockroom as a uniform dimming, and measured *no difference at all*
(29 % read at luma 144, 29 % at luma 62) — because a binariser normalises a
flat dimming away. That is not what a phone in a dark room produces: it gains
the sensor up, and the gain is noise. With noise and a longer exposure in the
model, the same frames read **47 % bright and 0–20 % dark**. Worth writing
down: the honest number only appeared once the model stopped being flattering.

### The figure of merit

Not "does this frame decode". A frame the decoder misses is not the end of a
scan — the hand moves and another frame arrives — so what decides whether a
code reads *first time* is

> how many independent chances fit into the second the owner holds the phone
> still, times how good each chance is.

`P(read within 1 s) = 1 − (1 − p)ⁿ`, and `n = 1000 ms ÷ (cost of one pass)`.
Expected reads per second of decoding (`n × p`) is the number every decision
below turns on.

## 2. What was measured, and what changed because of it

### 2.1 The two-frame confirmation — dropped for codes that check themselves

Every code had to be read on **two consecutive frames** before it counted.
Measured at the best framing:

| | one pass | passes in 1 s | P(read within 1 s) |
|---|---|---|---|
| confirm on 1 frame | 29 % | 14 | **99 %** |
| confirm on 2 frames | 29 % | 14 | **46 %** |

On the `--focus` run, with its harder frames: 82 % against 18 %.

That gap is most of what "hard and almost impossible" is made of. The
safeguard it bought — a curved-label misread — is **already bought by the
check digit**: EAN-8/13, UPC-A/E and CODE-128 all carry one, and zxing refuses
a code whose arithmetic does not add up. The code on the card is checked
arithmetic, not a guess, and the owner reads it before anything is bound.

**Changed:** `scanCameraRead(code, format)` takes the format now.
`ean_13 · ean_8 · upc_a · upc_e · code_128 · qr_code` count on the first
frame. **ITF and CODE-39 still need two** — ITF has no check digit at all and
CODE-39's is optional, so a single misread there is a plausible number rather
than an impossible one. Both decoders pass their format through: the native
`BarcodeDetector` gives it as a string, zxing as a numeric enum
(`zxingFormatName()`).

### 2.2 The framing — the 2× upscale was costing 2.7× the reads

The band under the scan line was `0.76 × 0.44` of the short side, **drawn at
2×** on the theory that an enlarged code reads better. It does not: upscaling
adds no information, and it made the pass four times as expensive.

Expected reads per second of decoding, all conditions (plain hints):

| framing (fractions are of the frame's short side) | per frame | passes/s | **reads/s** |
|---|---|---|---|
| `0.92 × 0.60`, drawn 1:1 | 20 % | 102 | **20.4** ← now |
| `0.76 × 0.44`, drawn 1:1 | 15 % | 126 | 18.9 |
| a full-frame-width band, `1.00 × 0.55` | 19 % | 66 | 12.5 |
| the whole frame, capped at 1280 wide | 15 % | 79 | 11.9 |
| the whole centre square | 16 % | 66 | 10.6 |
| **`0.76 × 0.44`, drawn at 2×** | 14 % | 53 | **7.4** ← was |
| the whole frame at 1920, uncapped | 16 % | 40 | 6.4 |
| `0.92 × 0.60`, drawn at 2× | 17 % | 35 | 6.0 |

**Changed:** the band is `0.92 × 0.60` of the short side, at the sensor's own
resolution, never enlarged. Wider than the drawn reticle on purpose — a code
inside the box always reads, one just outside it often does too.

It stays a **band** rather than the whole square: the one-dimensional reader
spreads a fixed number of scan lines over whatever height it is given, so a
taller image puts fewer of them across the code (the full square measured 23 %
per frame against the band's 29 %).

### 2.3 A crooked bottle — the one wall nothing else got over

| framing | 0° | 6° | 14° | 25° |
|---|---|---|---|---|
| the band, straight | 33 % | 33 % | 20 % | **0 %** |
| the band, turned back 13° | 27 % | 30 % | 37 % | **33 %** |
| either, or turned back −13° | 43 % | 43 % | 37 % | **33 %** |

Zero. Every framing, both decoders, `TRY_HARDER` included — zxing's thorough
mode retries at 90°, not at 25°. A bottle held a little crooked simply did not
read, ever, and no amount of holding it still would have helped.

**Changed:** the decode loop cycles four views of the band —
`[straight, +13°, straight, −13°]` — so every other pass covers the tilt, both
ways, and a code at 25° now has a real chance instead of none.

### 2.4 The decode cadence — 120 ms was throwing away most of the second

A pass costs ~10 ms with plain hints and ~90 ms with `TRY_HARDER` on this
hardware. The loop waited 120 ms between passes regardless.

**Changed:** `SCAN_TICK_MS` 120 → **60**, a floor rather than a wait. At ~20 %
per pass, 8 chances a second is 83 % inside a second and 16 is 97 %.

### 2.5 `TRY_HARDER` — off by default, on when the owner is clearly struggling

It reads about 9 points more of a single frame (29 % against 20 %) and costs
**eight to ten times as long**. Per unit of wall clock that is a bad trade
everywhere, and on a phone — three to five times slower than this desktop —
it is the difference between three chances a second and twenty.

**Changed:** the routine passes use plain hints. After **2.2 s with nothing
read** — the owner is holding the phone at a label and it is not working — the
thorough reader joins in on every other pass. Two readers, one stream.

### 2.6 The torch — comes on by itself in the dark

| | mean luminance | read rate |
|---|---|---|
| lit shelf | 140 | ~50 % |
| dark stockroom (dim + gain noise + longer exposure) | 62 | 0–20 % |

**Changed:** the band's mean luminance is sampled every eighth pass off a
32-px thumbnail. Below **80**, with a torch available and nothing read yet,
the torch comes on — **once**. The owner's own 🔦 stays the last word; a light
that switched itself back on after being turned off would be a light nobody
asked for.

### 2.7 The whole-frame pass — kept, but demoted from half the passes to a ninth

On the same frame, the whole frame catches ~1 point the band misses (band
29 %, either 30 %). It used to be **every other pass**. It is insurance for a
code that ended up outside the band, not the main event.

**Changed:** every ninth pass. Nine because it is coprime with the four tilts,
so it does not always steal the same one.

### 2.8 What was considered and not done

- **`ImageCapture.grabFrame()`** returns a frame at the *track's* resolution —
  the same pixels the preview already gives, which the loop already draws. No
  gain.
- **`ImageCapture.takePhoto()`** does reach full sensor resolution, but it
  costs a shutter cycle (hundreds of milliseconds) and on Android commonly
  interrupts the preview. At 20 reads per second of decoding from the preview,
  one 500 ms still frame would have to be worth ten ordinary chances. It is
  not. Written up as question 6 in case Dim wants it as a deliberate
  "take a proper photo of this stubborn label" button rather than as the loop.
- **Requesting more than 1920×1080.** The bench says the limit is not pixels
  but blur and tilt; a bigger frame costs decode time on every pass.

### 2.9 The honest limits of this bench

It measures the **zxing** half only: headless Chromium has no camera and no
`BarcodeDetector`. That is the half that matters — it is the floor under every
phone, and Android's native detector is strictly better where it works — but
the native path's own numbers are not measured here, only its schedule (which
is now shared, `scanViewCanvas()`, so the two cannot drift apart).

Absolute read rates are also not a prediction of the S21 FE. The sweep
deliberately includes conditions no one would call fair (mpx 1.2 is a code
115 px wide; blur 2.2 is a thrown phone). The *comparisons between settings*
are what it is for, and every one of them above is a comparison.

## 5. How to test it on the S21 FE — a fresh checklist for Dim

Steps 1–3 decide whether the camera can work at all; 4–9 are the new
behaviour. Where something is *supposed* to look different from yesterday it
says so.

1. **HTTPS, always.** `getUserMedia` is refused outside a secure context. The
   live domain is fine, a preview URL is fine, a `http://192.168.x.x` dev
   server is **not** — the screen will say «Нет доступа к камере
   (NotAllowedError)». Test on the deployed URL.
2. **Open `https://rempireshop.com/shop2/scan/`** and sign in once. Optionally
   add it to the home screen (Chrome: ⋮ → «Установить приложение»); the icon
   is «Сканер».
3. **Grant the camera as "While using the app"** — not "Only this time",
   which makes Android re-ask on every open.
   *To reset it later:* Chrome → the 🔒 icon left of the address bar →
   «Разрешения» → «Камера» → «Сбросить разрешения», then reload.
4. **The lens.** The picture should look like the ordinary photo camera, not a
   wide one — no curved edges, text sharp at 15 cm. If the first open looks
   wide, close and open once: the choice is remembered
   (`localStorage`, `rmp-scan-camera`).
5. **NEW — pinch.** Put two fingers on the picture and spread them. The
   picture should zoom and a small «2,4×» should appear at its bottom right
   for a moment. Pinch back in; it should follow. **Double-tap the picture**
   with one finger: it should jump out and, tapped twice again, come back.
   Close the scanner and open it again — it should still be where you left it.
   *If nothing happens at all,* this phone's camera reports no zoom capability
   — tell us, that is worth knowing.
   *The page under the viewfinder must not zoom or scroll while you pinch.*
6. **NEW — it should read on the first frame.** A code held reasonably still
   should beep and vibrate almost immediately, not after the "hold it a
   moment" pause it used to need. Try a **quick wave past a label**: it is now
   *allowed* to catch it. That is deliberate — the code carries a check digit
   the decoder verifies, and you see the digits on the card before anything is
   bound. **If you ever see a code that is not the one on the bottle, stop and
   tell us immediately** — that is the one thing this change could break, and
   it is the reason question 2 below is asked.
7. **NEW — a crooked bottle.** Hold the bottle so the barcode is 15–25° off
   horizontal. It used to be unreadable at that angle, full stop. It should
   read now, a little slower than straight.
8. **NEW — a dark corner.** Take a bottle somewhere dim. Within a second or so
   the torch should switch itself on. Tap 🔦 to turn it off and it must
   **stay** off for that session. (The button can take a second or two to
   appear on Samsungs — that has always been true.)
9. **NEW — «привязано N из M».** On «Склад», under «Сканировать», and on the
   scanner between codes. Bind one code: both numbers should be one apart from
   what they were. This is your progress bar for the ~220 bottles.
10. **NEW — the whole list.** «Склад» → scroll to the bottom. The list should
    keep loading more by itself, and «Показать ещё» is there if it does not.
    Get to the end: it should say «322 товаров» and offer no more button.
11. **NEW — one name.** «Товары» → «Склад»: there should be **one** scan
    button, in the body, saying «Сканировать». The «Приёмка» button that used
    to sit in the header is gone.
12. **What you should NOT see any more:** the line «Камера читает через
    запасной декодер…». If this phone's Play Services barcode module is
    broken we still learn it — it goes to the browser console now — but it is
    not Renat's problem to read.
13. **When it still fails,** in this order: wipe and flatten the label →
    press 🔦 → pinch in so the code fills more of the square → type the digits
    into «или введите код вручную» and press «Найти» (a first-class path, not
    a workaround) → a bluetooth/USB handheld scanner also works with the
    screen open and nothing focused.
    **What to send us:** which browser, whether the torch button appeared,
    whether the pinch did anything, and a photo of the barcode.

## 6. Questions for Dim

Numbered so they can be answered by number.

1. **Printing our own barcode labels.** You said «No, Renat will print them
   from system» — so nothing foreign gets stuck on a bottle, but the shop may
   need to *produce* a label. Nothing was built. What it would take, so you
   can price it: a route that renders a code (we already accept an internal
   alphanumeric form, e.g. `RMP-0042`, so no new format is needed) as a
   printable sheet — one per size, or a grid of them on an A4 of sticker
   paper, with the brand, the name, the size and the code under the bars.
   Roughly a day: the barcode drawing itself is ~80 lines (the bench already
   contains a working EAN-13 encoder), the rest is the print page and a
   «Печать этикеток» button on «Склад». **Three things to decide before it is
   worth starting:** (a) which items actually need one — sets, decanted
   product, salon-only items? (b) does Renat have sticker paper and would he
   print at home, or at a copy shop? (c) should the printed code be a real
   EAN-13 (needs a GS1 prefix, which costs money and only matters if the
   bottle ever leaves the shop) or an internal `RMP-…` code, which costs
   nothing and is enough for a warehouse?
2. **The one-frame rule leans on the check digit.** A code now counts the
   first time it is read, if it is a format that verifies itself. That is what
   makes the scanner feel instant, and it is the change most worth watching.
   Should we also keep a short in-memory log of the raw reads, so that if a
   wrong bottle is ever bound we can see whether the decoder misread or the
   finger did? (Cheap; nothing on screen.)
3. **The double tap.** You asked for a pinch and said it must work one-handed.
   A pinch needs two fingers, so a double tap on the viewfinder was added as
   the thumb-only version: out, then back. That is a design decision you did
   not make. Keep it, or is one gesture less to explain worth more?
4. **The automatic torch fires once per session.** If Renat turns it off, it
   stays off until he closes and reopens the scanner. Should it instead be
   allowed to come back on for the *next* bottle, or should there be no
   automatic torch at all and just the button?
5. **The «Склад» page size is 60.** With a scroll-to-load on top of it that is
   invisible in practice, but it is the number that decides how much the phone
   draws at once. Is there any screen where he wants the full 322 rows in one
   go (printing a shelf list, for instance)?
6. **A "take a proper photo" button?** Continuously decoding the preview beats
   a full-resolution still by a wide margin (a still costs a shutter cycle of
   several hundred milliseconds and often interrupts the preview), so it was
   not built into the loop. But for the one label that will not read at all, a
   deliberate «Сфотографировать код» that takes one full-sensor frame and
   decodes that might be the last resort before typing digits. Worth it, or is
   manual entry already that last resort?
7. **The fallback-decoder fact now goes only to the browser console.** Renat
   will never see it — which is what you asked — but neither will we, unless
   we ask him to open a console, which is not going to happen. Should the
   scanner quietly report it to the server once per phone (one tiny request,
   no personal data), so we find out which phones have broken Play Services
   without anyone having to notice?
8. **The «Товары» → «Склад» header now has no button at all** (it used to hold
   «Приёмка», and «Каталог» holds «+ Товар» there). It looks deliberate and
   the scan button is one line below, but if that corner looks empty to you,
   say so and something can go there — «История приёмок», for instance.
9. **`normEan()` still accepts the alphanumeric internal form** (4–32
   characters of letters, digits and hyphens), left alone on purpose because
   of question 1. If the answer to 1 is "never print anything", tightening it
   to digits only removes a class of misreads and should be done then.
