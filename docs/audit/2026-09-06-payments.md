# Online payments at checkout — audit and fixes, 06.09.2026

Scope: Montonio bank links, cards, Apple Pay / Google Pay, gift cards / points
/ promo covering the whole order, the return from the bank and the retry, the
mock provider's parity with Montonio, the admin order card's view of the
payment. Branch `r-payments` on top of `1a63cf8`. «Pay by invoice» belongs to
the invoice agent and was not touched (`PAYS[3]`, `S.invoiceCo`,
`[data-invoiceco]`, the top of `payNow()`'s chain).

Dim's three complaints, verbatim, and where each ended up:

- «when I made a gift card with 50 € and wanted to order something below that,
  it was not possible to make a purchase» → **B2** (fixed; plus the hole it
  would have opened, B3).
- «for Apple pay and gpay, I was routed to montonio bank payment again» →
  **B1** (fixed, client and server; the express button too, B5).
- «the whole payment at checkout needs a check» → sections **C** (what was
  swept and found sound) and **E/F** (what needs Dim's decision or a sandbox).

### Database (`db/migrations`)

`orders` (001, 060, 090/091, 100, 140): `status` ∈ new · paid · failed · shipped ·
delivered · cancelled · refunded; `subtotal`, `shipping_price`, `discount`,
`discount_code` (a gift code `RMP-…` **or** a promo), `loyalty_discount`,
`total`, `customer_id`, `channel`, `payment jsonb`. The blob (docs/payments.md
§8c): `provider`, `ref`, `status`, `method`, `bank`, `amount`, `currency`,
`detail`, `at`, `amountMismatch`, `rejected`. Around it: `gift_cards` /
`gift_card_uses` (020), `promo_codes` / `promo_code_uses` (060),
`loyalty_ledger` (100), `stock_levels` / `stock_moves` (090), `events` (080),
`admin_audit`. No migration was needed for this work.

### Statuses

Montonio `paymentStatus` → ours: `PAID`, `REFUNDED`, `PARTIALLY_REFUNDED` →
paid; `PENDING`, `AUTHORIZED` → pending; `VOIDED`, `ABANDONED`, `CANCELLED`,
`FAILED` → failed; anything unknown → pending (never failed). Order status
moves only new/failed → paid, new → failed; paid is never taken back by a
ticket (a late «failed» lands in `payment.rejected`).

### Env

`PAYMENT_PROVIDER`, `MONTONIO_ACCESS_KEY`, `MONTONIO_SECRET_KEY`,
`MONTONIO_ENV` (sandbox|live), `PUBLIC_BASE_URL` (the return and notify URLs
handed to Montonio), `SESSION_SECRET` (also derives the mock ticket key),
`RESEND_API_KEY` / `TELEGRAM_*` (the hooks). The e2e suite runs with
`PAYMENT_PROVIDER=mock`, `SHIPPING_PROVIDER=mock`, no mail keys.

### Test coverage before this work

Vitest: `payments-apply` (apply rules, idempotency, mock provider, revenue
row), `payments-montonio` (JWT, payload, statuses, tokens),
`payments-giftcard` (spent once, on paid), `payments-giftcard-issue` (cards
bought in an order survive a replay), `fuzz-money` (the whole path with
hostile bodies), `fuzz-routes`. E2E: `checkout.spec` (card pay / cancel × 3
languages, pickup), `giftcard.spec` (buy → issue → the discount shows),
`sweep-checkout` (ten random orders, a card worth more than the order —
asserted the *display*, never the payment), `account` / `admin` through
`payOrder()`. Nothing drove a wallet, a 0 € order, a retry, or read
`orders.payment` back.

## C. Swept and found sound (no change)

- **Double tap on «Оплатить»** — `S.paying` guards `payNow()` and now
  `payAgain()`; both buttons (summary and sticky bar) disable together.
- **No bank selected** — impossible: `S.bank` defaults to the first chip;
  reset to 0 when the real list lands; clamped when the country's list is
  shorter (B7).
- **Switching methods after picking a bank** — the code travels with a bank
  link only, on both sides.
- **Offline / static host** — `postJSON()` → `offline` → the demo receipt, as
  before.
- **Three languages** — every new storefront string has ET/EN; `node
  tools/i18n-gaps.mjs` → 0 untranslated. The mock bank page is Russian only
  by design (a developer's tool).
- **Phone width** — `e2e/payments.spec.ts` runs on `mobile-safari` (iPhone
  13, WebKit); the failed receipt's two buttons stack (`.done__acts`).
- **Webhook idempotency** — a second «paid» writes the blob and mints nothing,
  mails nothing, charges nothing; a late «failed» never takes paid back
  (`tests/payments-create.test.ts`, `payments-giftcard`, `fuzz-money`).
- **Amount mismatch** — taken and flagged (`payment.amountMismatch`), now
  visible on the order card.
- **Bank list degradation** — Montonio unreachable or no keys → `503
  not_configured` → the five built-in names with their BICs; a stale cached
  list is served while Montonio is down.
- **Mock = Montonio for all methods** — same options, same page semantics
  (B11); `e2e` stays representative.
- **Unpaid orders** — no stock is reserved (it is taken on paid), no cron
  expires them; they sit in «Ждут оплаты» (see E4).
- **Refunds** — `REFUNDED` keeps the order paid; the admin marks «Возврат» by
  hand; no refund API call (see E6).

## E. Questions for Dim

1. **The 0 € order's last step.** It works, but the button reads «Оплатить
   0 €» and the bank / card / wallet radios are still shown although nothing
   will be charged. Proposal: when `total() === 0`, hide the method block, show
   one line «Оплачивать нечего — заказ покрывает подарочная карта» (or
   «баллы» / «промокод») and label the button «Оформить заказ». Wording and
   layout are yours — not built.
2. **«…или выберите другой способ» on the failed receipt.** «Оплатить ещё
   раз» repeats the method chosen first. On Montonio's own page the shopper
   can still pick another *bank*; switching bank link ↔ card from the failed
   receipt is not possible. Add the three radios to that screen, or reword the
   sentence?
3. **Show the wallet option only when Montonio has card payments on?**
   `GET /api/payments/methods/` already answers `card: true|false`; today the
   wallet and card radios are always shown. Also: on Montonio's card page
   Apple Pay appears only in Safari / on iOS, Google Pay in Chrome — should the
   option's hint say so («Apple Pay в Safari, Google Pay в Chrome»), or leave
   «Оплата в одно касание»?
4. **Orders that never get paid.** They stay «new» / «не оплачен» forever, in
   «Ждут оплаты». No stock is held for them (taken on paid — correct), so the
   only cost is the list. Auto-cancel after N days (7? 30?), or leave to
   Renat? The «заказ ждёт оплаты» reminder letter exists
   (`settings.flows.pending`) — confirm whether it should be on at launch.
5. **Duplicate «new» orders on a failed create.** If `create` fails
   (Montonio down), the cart stays and a second tap on «Оплатить» makes a
   *second* order. Fix = remember the order id in the checkout and reuse it
   while the basket is unchanged — it touches the top of `payNow()`'s chain,
   which the invoice agent is editing, so deliberately postponed to after the
   merge.
6. **Refunds.** Montonio's `REFUNDED` / `PARTIALLY_REFUNDED` keep the order
   paid and its refund webhooks are now acknowledged and ignored; «Возврат» in
   the admin is a status only. Should the admin card call Montonio's refund API
   (full / partial) — a real feature with its own sandbox check — or stay
   manual (refund in Montonio's partner system, then mark here)?
7. **A 0 € order with «По счёту» chosen.** The invoice agent's branch runs
   before `payments/create`, so a fully covered order would still get an
   invoice for 0 €. My suggestion for the merge: skip the invoice when
   `total() === 0` and let the create route settle it. Their call, flagging it.
8. **Manual «отметить оплаченным» in the admin** duplicates the settle steps
   by hand (`src/app/api/admin/orders/[id]/route.ts`) instead of calling
   `settlePayment()`. Works today; whoever owns the admin should switch it so
   the four doors into «paid» cannot drift.

## F. Risks before Montonio goes live

1. **Sandbox assumptions still unverified** (docs/payments.md §6): the BIC
   codes as `preferredProvider`, `locale: "ru"`, `AUTHORIZED` never arriving,
   the `uuid` vs `id` field. One sandbox order per method (bank, card, wallet)
   settles all of them.
2. **Return and webhook racing on the first «paid».** Both read the order
   before either writes it; both can see «new» and both run the side effects.
   The customer letter is deduped by Resend's idempotency key and every
   ledger write is idempotent, but the owner's Telegram ping and the purchase
   event could double. Low probability (Montonio's webhook usually lands
   seconds after the redirect), fix is a conditional `UPDATE … WHERE status
   NOT IN ('paid',…) RETURNING` claim on the paid transition — small, but in
   `setOrderStatus()` / `apply.ts`, shared code; worth doing in a quiet
   moment before go-live.
3. **`PUBLIC_BASE_URL`** must be the public domain on production, or the
   return/notify URLs handed to Montonio are whatever host header the proxy
   passed on.
4. **Apple Pay on Montonio's page** needs Montonio to have it enabled for the
   store (and their domain registered with Apple) — nothing in this repo can
   do that; test on a real iPhone in the sandbox.
5. **The mock provider** must never be set on production
   (`PAYMENT_PROVIDER=mock` mints paid tickets from `SESSION_SECRET` alone) —
   already guarded, restating it because the 0 € path now needs no provider
   and could mask a missing `PAYMENT_PROVIDER` in a smoke test that only buys
   with a gift card.
6. **Rate limits**: `create` 20/min per IP — an office behind one NAT placing
   many orders could hit it; harmless, worth knowing when reading logs.
