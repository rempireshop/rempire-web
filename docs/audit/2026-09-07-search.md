# Search: what the shopper means

07.09.2026, branch `r3-search3` off `874437e`. Dim: «teeme searchi targemaks ja
las otsib AI'ga üle lehe — näiteks "rasvased juuksed" — not only word-for-word
search capability.»

The shop's search screen, the results list and the owner's «Искали, но не
нашли» report are **unchanged**: this is entirely about what the search FINDS.
Everything that needed a visible change is a numbered question at the end.

---

## 1. How it worked until today

One function, six lines, `public/shop2/app.js`:

```js
function searchResults() {
  var q = S.query.trim().toLowerCase();
  if (!q) return [];
  var words = q.split(/\s+/).map(stem);
  return CATALOGUE.filter(function (p) {
    var hay = (p.name + " " + p.brand + " " + CAT_NAMES[p.cat]).toLowerCase();
    for (var i = 0; i < words.length; i++) if (hay.indexOf(words[i]) < 0) return false;
    return true;
  });
}
```

Every word of the query, stemmed by cutting up to two trailing letters, had to
appear as a **substring of the product's name, brand or section name** — and of
nothing else. `CATALOGUE` comes from `public/shop/catalogue2.js` (220 rows:
id, brand, name, section, price, sizes, stock), which is where the search's
whole world ended.

Around it:

* `screenSearch()` renders the box, the count, the grid and the empty state
  («По запросу «…» ничего не нашлось»), plus five «popular query» chips.
  Nothing here changed.
* `scheduleSearchTrack()` fires one `track("search", {path: q, value: n})`
  700 ms after the last keystroke. `db/migrations/080_events.sql` documents the
  repurposing: for a search row `path` holds the query text and `value` the
  result count, so «Искали, но не нашли» is `where type='search' and value = 0`
  (`qSearchTerms()` in `src/lib/analytics.ts`).
* `src/lib/catalogue-slice.ts` — the *server's* keyword scorer, used by the
  chat and the article generator. Same blind spot (`p.b + p.n + p.id`), but a
  different job; untouched.

**What that could not find.** The descriptions were never searched — and every
one of the 220 products has a full description in **all three languages**
(`public/shop/content.js` EN, `content.ru.js`, `content.et.js`, ~920 KB,
already loaded on every page). So:

* «rasvased juuksed» / «жирные волосы» / «oily hair» → nothing. No product is
  named that; thirty products are *described* that way.
* «перхоть» → nothing. Fifteen mentions of dandruff in the descriptions.
* «система 4» and «систем 4» → nothing, because the brand is written `System 4`
  in the Latin alphabet. These are **real Google queries this shop is found
  by**, eight of them in the last 28 days.
* «шампунь номер 1», «creed aventus 50ml», «kevin murphy freehold» → nothing,
  because one word of the query was missing from the name.

## 2. What was built

### Pass 1 — names and brands, word for word as before

`searchNames()` is the old function, quoted, not rewritten. It runs first, and
when it returns **six products or more** (`SRCH_WIDEN`) nothing else runs at
all: «Davines», «шампунь» and «un.tangled» are as instant and as exact as
yesterday.

### Pass 2 — the product's own text, three languages at once

Below six, `searchWide()` looks the same words up in a per-product index built
from name, brand, section, volumes, the description the page shows (the owner's
override first, the static text after) and the Google title/description. Two
normalised strings per product, 528 KB over 220 products, built **lazily** on
the first widened search of a session (~30 ms on this desktop) and thrown away
whole (`SRCH_IX = {}`) in `applyDemoOverrides()` and `rebuildCatalogue()` — so
a description the owner saved a minute ago is searchable. The index sits
*beside* the products, keyed by id, rather than on them: a product row is
passed around `app.js` freely, and half a megabyte of search text bolted onto
it would sooner or later travel inside an order body or into `localStorage`.

Costs **nothing per query**: no request, no server, no key. The shop still
works with the API entirely absent.

Inside it, the parts that make three languages meet:

* **Normalisation** (`srchNorm`) — lower case, ё → е, õäöüšž → oaousz via
  NFD, every other non-letter a space, and a digit always parted from a letter
  («100ml» → «100 ml», «4system» → «4 system», both real queries). Matching is
  `indexOf(" " + word)` — a word-START test, so «murphy» finds «Kevin.Murphy»
  and «ampoo» finds nothing.
* **Stemming** (`srchStem`) — one ending off, two tables and two floors.
  Russian keeps three letters («жирный/жирные/жирным» → «жирн», «сухая» →
  «сух»); the Latin alphabet keeps four, and that second floor is not a detail:
  at three, «creed» became «cre» and found every «cream» in the shop.
  Estonian is covered by the same cut plus prefix matching — «rasvased» → «rasva»,
  «rasvastele» → «rasvas», each a prefix of the other's written form.
* **Bridges** (`SRCH_BRIDGE`, ~90 rules) — one query word → the other spellings
  this catalogue uses. Product words («шампунь» → shampoo, «seerum» → serum),
  concern words («жирн» → oily, greasy), and the brands written in Cyrillic
  that Search Console actually shows: «систем» → system, «наксос» → naxos,
  «крид авентус» → creed aventus, «биоботаническая» → bio botanical.
* **Most words, not every word** — from three words up, one word in three may
  be missing, provided at least one of the rest is in the product's own name.
  This is what «system 4 nr. 2 climbazole shampoo 500 ml» and «how to apply
  kevin murphy plumping wash» needed. A bare number never has to be found
  («creed aventus 50ml» is a person asking for Creed Aventus, and our row for
  it has no 50 ml rung).

### Pass 3 — the concern table

`SRCH_CONCERNS`, 19 entries. Each is: the phrase a person types about
themselves (`q`), what rules that reading out (`n` — «жирная кожа ГОЛОВЫ» is a
scalp, not a face), the words the catalogue itself uses (`t`), and the sections
it can be in at all (`c`). Oily hair, oily skin, dandruff, hair loss/thinning,
dry scalp, dry/damaged hair, volume, split ends, itchy scalp, coloured hair,
curly hair, acne, wrinkles, pores, dry skin, sensitive skin, beard care,
shaving irritation, hold/matte styling.

A concern's sections also bind the plain word matching, which is what keeps
«объём волосам» from returning a beard oil whose text happens to say «volume»
and «hair».

Everything in these tables is a **regex literal, never a string**, and written
in the folded spelling `srchNorm()` produces. That is not style: these are
Cyrillic matching keys nobody will ever see, and `tools/i18n-gaps.mjs` is right
to demand a translation for every Russian *string* that could reach the screen.

### Pass 4 — the model, and only here

`POST /api/search` (`src/app/api/search/route.ts`, `src/lib/search-terms.ts`).
The storefront asks **once per phrase per session**, only after the three free
passes came back below six, and only 700 ms after the last keystroke — the same
debounce the analytics beacon already waits for. The model is given the shop's
sections and its 26 brands and asked for up to eight terms that would be
*printed in* a product text; it is told to answer with an empty list rather
than guess. What comes back is sanitised to short plain terms
(`cleanSearchTerms`) and fed straight back into `searchWide()`.

**The model never writes a word the shopper reads.** Its output is search terms
and only search terms: a wrong answer costs a few odd cards on a page that was
empty anyway.

Guards, the same posture as the other AI routes: no `OPENAI_API_KEY` → 503 and
the storefront stops asking for the session; same-origin only; 12 calls a
minute per IP; temperature 0, `json_object`, 120 output tokens. Every failure —
503, 403, 404 (a static copy of the shop with no server at all), 429, 502, an
offline phone — leaves the results already on screen and says nothing.

Answers are cached 24 h per instance, **including empty ones**: «где мой заказ»
has no catalogue words behind it, and remembering that is what stops the next
visitor who types it from costing anything.

**Two things a real browser found that no unit test would have.** The
storefront's `fetch` had to be `/api/search/` **with** the trailing slash —
`trailingSlash: true` in `next.config.ts` turns a POST without it into a 308,
which browsers do follow but at the price of a second round trip. And the ask
had to be hung off `trackNav()`, not only off the input handler: a reload, a
shared `/search/?q=…` link and the Back button all land on the search screen
with a query already in the address, and nobody typed. That second fix also
closes an older hole — until today a *reloaded* search filed no search event at
all, so it never reached the owner's report either.

### The owner's report

Two things, and neither of them changes the report's screen:

1. The search event now **waits** for the model's answer before it is written,
   so `value` is the number of products the shopper really ended up seeing. A
   query that now succeeds therefore leaves «Искали, но не нашли» by itself —
   that report is `value = 0` and nothing else.
2. When the model is what found them, the event carries `product_id = 'ai'`.
   `db/migrations/080_events.sql` leaves that column free on a search row, and
   nothing reads it today, so the report looks exactly as it did. The list of
   phrases the assistant had to rescue — the list Renat should turn into real
   product texts — is one query away:

```sql
select path as "искали", count(*) as "раз", max(at) as "последний раз"
from events
where type = 'search' and product_id = 'ai' and at > now() - interval '28 days'
group by 1 order by 2 desc;
```

Question 1 below asks whether that should become a line in the panel.

first three passes could not answer — that is, on a screen that was about to be
empty anyway; a phone will take a few times longer. Each widened query after
that is **~4 ms**, and one query's answer is cached, so re-rendering on a
keystroke is free. Nothing is built at boot: a visitor who never searches pays
nothing at all.

## 4. What the model adds, and what it costs

**What it adds.** It is the answer to a phrase in a language nobody wrote a
table for, a misspelt brand, and a way of putting it the shop's own words do
not cover. In the 554-query sample that is at most 54 phrases, ~10 %, and only
the first time each is typed. Every one of the 500 the shop can answer itself
is answered **without the model** — it is never in the path of a query the free
passes could handle, which was the point of doing them first.

**What it costs.** One request: ~250 input tokens (the system prompt is fixed
and short — sections, brands, four rules) and ~40 output. On the default
`gpt-4.1-mini` (`OPENAI_MODEL`) that is roughly **€0.00015 — about one and a
half hundredths of a eurocent per new phrase**, or ~15 cents for a thousand
phrases nobody has ever typed here before. Repeats are free for 24 hours.

At this shop's traffic — a few hundred internal searches a month — the honest
number is **under one cent a month**. The ceiling if somebody sat on it: 12
calls a minute from one IP ≈ €1.50 a day sustained, which is why question 4
asks whether a hard monthly stop is wanted.

**What it cannot do.** Write. It never produces a sentence, a product name or a
price; it hands back words, they are matched against text the shop wrote, and
what the shopper sees is product cards and nothing else.

## 5. Questions for Dim

1. **Should «Искали, но не нашли» gain a second line — «Нашёл помощник»?**
   The data is being recorded now (`product_id = 'ai'` on the search event) and
   the SQL is in §2 above, but the report's screen was left exactly as it is
   because you asked for no UI changes. That list is the most useful thing on
   this page for Renat: it is precisely the phrases his product texts do not
   cover yet. Adding it is ~10 lines in `analytics.ts` and ~5 in the panel —
   but both files belong to other agents this week, so it needs saying out loud
   before anyone touches them.

2. **Should the shopper be told the assistant is looking?** Today the empty
   state («ничего не нашлось») appears, and about a second later the products
   quietly appear under it. It works, but the second in between reads as "no
   results" when the honest word is "one moment". The smallest possible version
   is one grey line under the box. Your call — this is a visible change.

3. **Should «подарок» / «kingitus mehele» find the gift card and the sets?**
   It is the one concern phrase still returning nothing, and rightly: the
   search only ever returns products from the catalogue, and the gift card and
   the «Наборы» are not products. Making it work means the results list can
   contain something that is not a product card — a real UI decision.

4. **A hard ceiling on the assistant's search spend?** There is a per-IP limit
   (12/min) and a 24 h cache, and the realistic bill is under a cent a month.
   There is no global stop. Options: a monthly counter that switches pass 4 off
   at, say, €2, or nothing at all on the grounds that the per-IP limit is
   already the fence.

5. **Does the shopper's typed phrase going to OpenAI need saying in the privacy
   text?** Only phrases the shop itself could not answer leave the server, and
   nothing travels with them — no id, no cookie, no address. It is the same
   posture the shop chat already has (`/api/assistant`), which the consent
   banner does not mention either. Two consistent answers exist: say it once in
   «Данные и cookie» for both, or leave both as they are. A lawyer should
   probably pick.

6. **Who keeps the concern table?** Nineteen entries cover what we could see in
   the data today. The list that says what is missing writes itself — it is
   question 1's report. Should adding a concern be a developer's job, or should
   Renat get a two-column screen for it later («когда ищут вот так — показывай
   вот это»)?

7. **One pre-existing gap fixed in passing, for the record.** `node
   tools/i18n-gaps.mjs` printed 1 untranslated string at `874437e` — an admin
   hint in the goods editor's sizes pane, added without its ET/EN pair. It is
   translated here (two dictionary lines) so the tool prints **0**. It belongs
   to the inventory work; if that agent translates it too, the merge will show
   a duplicate key and `i18n-gaps` will say so.
