# Оплата — Montonio, тестовый режим и что настроить

Магазин принимает деньги через **Montonio** (банковские ссылки Swedbank / SEB /
LHV / Luminor / Coop и карты Visa / Mastercard). Пока ключей нет, работает
встроенный тестовый «банк» — весь путь заказа можно пройти на ноутбуке, ничего
не подключая.

Файлы: `src/lib/payments/`, маршруты `src/app/api/payments/*`, документация
Montonio — <https://docs.montonio.com/api/stargate/guides/orders> (сверено
03.09.2026).

---

## 1. Что нужно сделать Ренату (один раз)

1. Зарегистрировать магазин в песочнице: <https://sandbox-partner.montonio.com>.
   Песочница — это полная копия боевой системы, но без настоящих денег; для неё
   не нужен договор и не нужна проверка бизнеса.
2. В песочнице: **Stores → выбрать магазин → API keys**. Там два значения:
   - **Access Key** — публичный идентификатор магазина;
   - **Secret Key** — им подписывается каждый запрос. Его нельзя показывать
     никому и нельзя класть в git.
3. Прислать оба ключа Дмитрию **не почтой и не в чате** — лучше через менеджер
   паролей или голосом. Дмитрий положит их в переменные окружения Vercel.
4. Когда всё проверено в песочнице — подать заявку на боевой доступ
   (<https://partner.montonio.com>). Montonio проверяет бизнес: нужны реквизиты
   Rempire Store OÜ, сайт с условиями и политикой возврата (они уже есть в
   `/shop2/info/...`) и банковский счёт для выплат.

## 2. Переменные окружения

Значения не хранятся в репозитории — только имена.

| Переменная | Что это | Обязательна |
| --- | --- | --- |
| `PAYMENT_PROVIDER` | `montonio`, `mock` или `makecommerce`. Не задана — Montonio, если есть ключи, иначе `mock`. | нет |
| `MONTONIO_ACCESS_KEY` | Access Key из партнёрской системы | для Montonio |
| `MONTONIO_SECRET_KEY` | Secret Key, им подписывается JWT | для Montonio |
| `MONTONIO_ENV` | `sandbox` (по умолчанию) или `live` | нет |
| `PUBLIC_BASE_URL` | Публичный адрес магазина, например `https://rempireshop.ee`. Без него берётся адрес из запроса. | на бою — да |
| `SESSION_SECRET` | Подписывает билеты тестового провайдера (и админ-сессию) | да |

**Не переключайте `MONTONIO_ENV` на `live`, пока боевые ключи не выданы** —
песочные ключи на боевом хосте не работают, и наоборот.

## 3. Вебхук

В партнёрской системе регистрировать ничего не нужно: адрес уведомления
уходит в каждом заказе (`notificationUrl`). Он такой:

```
https://<ваш-домен>/api/payments/notify/
```

Слэш в конце обязателен — в `next.config.ts` включён `trailingSlash`, и без
него POST превращается в 308.

Что важно знать про вебхук:

- Montonio шлёт его с адресов `35.156.245.42` и `35.156.159.169`. Если перед
  сайтом появится Cloudflare или файрвол — эти адреса нужно пропустить.
- Если ответ не 200/201, Montonio повторяет доставку **48 часов**. Наш маршрут
  отвечает 200 на всё, что понял (включая повторы), и 400 только на подпись,
  которую нельзя проверить, — повторять такое бессмысленно.
- Вебхук и возврат покупателя приходят одновременно и наперегонки. Правило
  одно: **оплачённый заказ уже не отменяется** (`src/lib/payments/apply.ts`).
  Поздний «не оплачен» записывается в `payment.rejected`, чтобы это увидел
  человек, но статус заказа не трогает.

## 4. Тестовый провайдер (без ключей)

`PAYMENT_PROVIDER=mock` (или просто отсутствие ключей Montonio) включает
страницу `/api/payments/mock/` — вместо банка две кнопки, «Оплатить» и
«Отменить». Дальше всё идёт настоящим путём: тот же возврат, та же проверка
подписи, тот же экран чека.

```bash
# полностью локально: база в памяти, ключей не нужно
# (каталог для PGlite — вне репозитория, чтобы не попал в git)
export DB_DRIVER=pglite PGLITE_PATH="$TMPDIR/rempire-pgdata"
export PAYMENT_PROVIDER=mock SESSION_SECRET=local-dev-secret-16
npm run migrate && npm run dev
```

Билет тестового «банка» — настоящий подписанный JWT (ключ `SESSION_SECRET`),
так что чужой заказ им пометить оплаченным нельзя.

## 5. Как проверить песочницу

1. Поставить `MONTONIO_ACCESS_KEY`, `MONTONIO_SECRET_KEY`, `MONTONIO_ENV=sandbox`.
2. Оформить заказ в магазине.
3. На странице Montonio выбрать любой тестовый банк — в песочнице они всегда
   подтверждают оплату; карту можно проверить тестовой картой Adyen
   `4111 1111 1111 1111`, срок `03/2030`, CVC `737`.
4. Вернуться в магазин: адрес должен быть
   `/shop2/done/?n=R-1000xx&s=paid`, а заказ в админке — «оплачен».
5. Локально вебхук не долетит (`localhost` снаружи не виден) — для проверки
   поднять туннель (`ngrok http 3300`) и выставить `PUBLIC_BASE_URL` на его адрес.

## 6. Что именно уходит в Montonio

Заказ подписывается JWT (HS256, живёт 10 минут) и уходит POST-ом на
`https://sandbox-stargate.montonio.com/api/orders` (или без `sandbox-` на бою)
в виде `{ "data": "<jwt>" }`. Ответ содержит `paymentUrl` — туда уходит
покупатель — и `uuid`, который мы храним у заказа.

Поля payload взяты дословно из документации Montonio: `accessKey`,
`merchantReference` (наш номер заказа, `R-100042`), `returnUrl`,
`notificationUrl`, `currency`, `grandTotal`, `locale`, `exp`, `billingAddress`,
`shippingAddress`, `lineItems[{name, quantity, finalPrice}]` и `payment`
(`method`, `methodDisplay`, `amount`, `currency`, `methodOptions`).

Возврат приходит как `?order-token=<jwt>`, вебхук — как `{"orderToken": "<jwt>"}`;
оба проверяются тем же секретом и содержат `paymentStatus`.

### Допущения, которые надо подтвердить в песочнице

Всё, что ниже, — не выдумка, но и не то, что видно из документации напрямую.
Проверить при первом же тестовом заказе:

1. **Коды банков.** `payment.methodOptions.preferredProvider` мы шлём как BIC:
   Swedbank `HABAEE2X`, SEB `EEUHEE2X`, LHV `LHVBEE22`, Luminor `RIKOEE22`,
   Coop `EKRDEE22` (`public/shop2/app.js`, `BANK_CODES`). Авторитетный список —
   `GET /stores/payment-methods`, поле `code`. Если код неверный, Montonio
   просто покажет покупателю выбор банка сам — не смертельно, но лишний шаг.
2. **`locale: "ru"`.** В документации русский указан среди допустимых значений
   (`de, en, et, fi, lt, lv, pl, ru`). Стоит убедиться, что страница оплаты
   действительно открывается по-русски.
3. **Статусы.** Мы раскладываем `paymentStatus` так: `PAID` → оплачен;
   `PENDING`, `AUTHORIZED` → ждём; `VOIDED`, `ABANDONED` → не оплачен;
   всё незнакомое → «ждём» (никогда не «не оплачен»). `AUTHORIZED` включается
   отдельно по заявке, у нас его быть не должно.
4. **`VOIDED`** — редкий случай, когда банк отменяет уже оплаченный платёж.
   Мы такой заказ автоматически не отменяем (см. выше про идемпотентность);
   Montonio при этом пишет письмо владельцу магазина. Если такое случится —
   заказ правится в админке руками.

## 7. MakeCommerce

`src/lib/payments/makecommerce.ts` — заглушка: все методы кидают
`not_implemented`, и сам по себе этот провайдер не включается никогда (только
явным `PAYMENT_PROVIDER=makecommerce`). Он существует, чтобы выбор между
Montonio и MakeCommerce остался правкой одного файла: интерфейс
(`createPayment` / `verifyReturn` / `verifyNotification`) у них одинаковый,
отличается только конверт — у MakeCommerce Basic-авторизация вместо JWT и
подпись `mac` (SHA-512) вместо токена.

## 8. Коды ошибок API

`POST /api/payments/create/` возвращает `{ok:false, error:"<код>"}`:

| Код | Что случилось |
| --- | --- |
| `missing_order` / `not_found` | Не передан или не найден заказ |
| `already_paid` / `order_closed` | Заказ уже оплачен, отменён или возвращён |
| `bad_amount` / `bad_order` | Сумма нулевая или заказ без номера |
| `provider_unconfigured` | Выбран Montonio, но ключей нет |
| `provider_unreachable` / `provider_rejected` | Montonio не ответил или отказал |
| `db_unavailable` | База недоступна |
| `rate_limited` | Больше 20 попыток в минуту с одного адреса |
